# Demo Workspace

The Demo Workspace is a deterministic, fictional production-order dataset for exercising the real ScrapLess application. It contains **25 orders**, **220 part types**, and **876 requested part instances** across Mild steel, Aluminium, and Stainless steel. The dataset includes 5 small-batch, 12 mixed-production, and 8 high-volume orders, plus urgent/low-priority work, varied stock sheets and prices, and rotation-sensitive configurations.

The customer and company names are fictional. Order creation/due dates are simulated historical dates and are labelled in Orders, Analytics, and History. Placements, utilization, waste-area proxies, sheet counts, comparisons, and costs are calculated from the existing FFD and MaxRects BSSF algorithms; they are not seed-time estimates or hardcoded dashboard metrics. AI risk predictions still use the application's synthetic model and must not be interpreted as calibrated probabilities.

## Load and reset

1. Start the backend and frontend using the [local setup instructions](../README.md#local-setup-windows-powershell).
2. Open `http://localhost:3000/dashboard` and choose **Load Demo Workspace** (also available from Settings).
3. Review the confirmation and choose **Confirm and load**. The app persists missing demo orders, checks for existing valid FFD/MaxRects pairs, then processes remaining orders in batches of five through FastAPI.
4. Follow the progress message. The completion report distinguishes newly inserted orders, existing orders reused, validated order pairs, algorithm results generated during this run, and per-order failures. A partial failure does not stop later batches.
5. Inspect Orders, choose a saved order in the optimizer, run/inspect both layouts, and visit Analytics, AI Insights, History, or Vision.
6. To remove the dataset, choose **Reset demo data** and confirm. Only rows with `demo_dataset_id = apex-industrial-components-v1` are selected for deletion. Normal user orders and non-demo optimization results are not targeted.

Loading repeatedly is idempotent: demo orders are identified by their stable IDs and dataset marker; existing matching orders are not overwritten. If a normal order already occupies a demo ID, the loader reports a collision instead of replacing it.

## Development demo mode versus authenticated mode

### Development demo mode

- Requires no Supabase credentials; do not set only one of `SUPABASE_URL` and `SUPABASE_ANON_KEY`.
- Production orders are stored in the browser's local storage and survive navigation and reloads in that browser.
- Computed optimization history uses the backend's bounded in-memory store. It is not durable and is cleared by a backend restart.
- Reset removes only the local orders carrying the dataset marker and in-memory runs generated by the demo batch endpoint.
- This mode is for local development and must not be exposed as a production service.

### Authenticated Supabase mode

- Sign in with the user's own Supabase account. The frontend inserts missing orders with that user's ID using the anon key and owner-scoped RLS; it never uses a service-role key.
- The frontend sends the signed-in access token to the FastAPI batch endpoint. FastAPI validates it with Supabase Auth and persists both algorithm records using the same user token and the existing owner-only `optimization_runs` RLS policy.
- Demo dates are explicitly supplied for demo run records and identified by the dataset marker. Algorithm outputs are computed at load time.
- Reset deletes only the current authenticated user's demo-marked run records and orders.
- Live Supabase Auth, RLS, and persistence have not been verified against a user's project as part of this implementation. Automated auth/persistence tests use mocked Supabase responses.

Before using authenticated demo data, apply these migrations manually in order if they have not already been applied:

1. `supabase/migrations/202611250001_initial_schema.sql`
2. `supabase/migrations/202611260001_demo_workspace_metadata.sql`

The second migration adds nullable `demo_dataset_id` markers to production orders and optimization runs, a JSONB `metadata` field to production orders, and partial owner/dataset indexes. It does not change RLS policies and is safe to apply after the initial schema. **No SQL was executed by the application or during development of this feature.**

Frontend public configuration remains `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `NEXT_PUBLIC_API_URL`. For authenticated backend operation also configure `SUPABASE_URL` and `SUPABASE_ANON_KEY` on FastAPI. No service-role key or additional environment variable is introduced.

After loading data into an authenticated project, a user can verify ownership and counts with read-only queries in Supabase SQL Editor:

```sql
select demo_dataset_id, count(*)
from public.production_orders
where demo_dataset_id = 'apex-industrial-components-v1'
group by demo_dataset_id;

select demo_dataset_id, algorithm, count(*)
from public.optimization_runs
where demo_dataset_id = 'apex-industrial-components-v1'
group by demo_dataset_id, algorithm
order by algorithm;
```

Expected complete-workspace counts are 25 orders and 25 records per algorithm (50 result rows). Counts can be lower after partial failures, reset, or if an order ID collision was reported.

## Regenerate demo data and assets

From the repository root in PowerShell, with backend dependencies installed:

```powershell
.\.venv\Scripts\python.exe .\backend\scripts\generate_demo_assets.py
```

The generator uses a fixed random seed and a fixed reference date. It writes:

- `backend/data/demo_orders.json`
- `backend/data/demo_cutting_layout.png`
- `frontend/public/demo/basic-parts-sample.csv`
- `frontend/public/demo/production-order-parts-sample.csv`

Commit regenerated assets together with the generator if the dataset is intentionally changed. `backend/app/demo_data.py` validates the checked-in JSON against the Pydantic order, sheet, and metadata models before serving it.

## CSV import

The Orders page provides downloadable **Basic CSV** and **Production CSV** examples. The importer accepts UTF-8 CSV with required columns `part_id`, `length`, `width`, and `quantity`; optional columns are `priority`, `material`, and `description`. CSV contains a single part list, not the additional order-level metadata in the Demo Workspace. Validate the downloaded file on the Orders page, review the populated order form, and save it before optimizing.

## Computer-vision example

The Vision page's **Use included sample image** action retrieves the checked-in PNG from FastAPI. **Download sample image** is also available. The included image has eight separated dark rectangular pieces on a light sheet and is processed by the same OpenCV endpoint as any uploaded image. Detection candidates and the annotated output are actual OpenCV results in pixel coordinates. The feature is experimental; it does not infer calibrated physical dimensions or guarantee part recognition.

## Known limitations

- In development mode, backend optimization history is memory-only; a backend restart requires rerunning the demo optimizations.
- In authenticated mode, the metadata migration must be applied before the orders UI can select the new columns and before demo seeding/reset is available.
- The batch endpoint accepts up to five canonical orders and 500 aggregate instances per request, and is rate-limited. Backend concurrency and normal optimization request limits remain active.
- Demo timestamps are simulated; they do not represent real customer production events. Demo runs are marked in storage and in the UI.
- The risk model is synthetic and uncalibrated. OpenCV output is a set of candidate contours, not a production-ready part measurement system.
- No live Supabase account or hosted deployment was used for verification.
